# CI and release publishing

Public pull requests run `make test`, all role builds, contract checks, and the Docker-free production runtime suite with read-only repository permission and no secrets. A successful trusted `main` push, or manual execution whose ref is explicitly `main`, repeats that gate before publishing four `linux/amd64` role images to `ghcr.io/<owner>/rogi-collector-{discover,coordinator,worker,query}`.

Repository variables `POSTGRES_IMAGE` and `REDIS_IMAGE` must be reviewed immutable digest references. The publisher writes those and the four built image digests into `manifest.build.json`. It publishes public GitHub Release assets `release-bundle.tar.gz` and `release-bundle.tar.gz.sha256`, and retains the same files as the `rogi-collector-production-release` Actions artifact. The bundle contains only the allow-listed release source and build-owned manifest fields. Runtime host configuration, secrets, tokens, account identifiers, and state are excluded.

Hosts poll the public Releases API no more often than every five minutes, accept only a release tied to a successful `release.yml` main push, verify the release/source SHA and checksums, and merge the root-owned runtime overlay. Public Release assets are checksummed metadata/source bundles; GHCR images remain private. A matching `private-deploy` run supplies the short-lived credential and invokes the fixed deployment path for a new private digest. The release publisher itself never applies infrastructure or connects to EC2.

A rerun never overwrites a published SHA tag, image tag, or Release asset. If `production-<sourceSha>` already exists, the workflow verifies its asset checksum and embedded source SHA and skips all publishing; malformed or conflicting existing assets fail the run. Published images carry OCI `org.opencontainers.image.source` and `org.opencontainers.image.revision` labels.

The trusted release job emits a GitHub artifact provenance attestation for `release-bundle.tar.gz` using OIDC. Host enforcement remains checksum, source/tag, and successful workflow verification until an approved, checksum-pinned GitHub CLI verifier and its authentication/public-access contract are installed; the attestation is not yet claimed as a host admission gate.

`public-source-audit.yml` checks every push and pull request with read-only repository permission. It fetches full available Git history, verifies the official Gitleaks v8.30.1 Linux x64 archive against the release checksum (`551f6fc83ea457d62a0d98237cbad105af8d557003051f41f3e7ca7b3f2470eb`), and scans committed history with redacted output. No allow-list or generated-file exclusion is configured.

`private-deploy.yml` is a separate privileged `workflow_run` consumer. It runs only after this repository's `release` workflow succeeds for a `push` on `main`; it never checks out or executes the triggering revision. GitHub OIDC assumes the repository-scoped AWS role, stores the current job's short-lived packages-read token as exact `{username,token}` JSON in the dedicated registry Secrets Manager entry, invokes the fixed SSM deployment document for the product, waits for completion while the token remains valid, and overwrites the registry secret with empty values on every exit. EC2 receives no human PAT or long-lived GitHub credential. Required repository secrets are `AWS_DEPLOY_ROLE_ARN`, `AWS_INSTANCE_ID`, `AWS_REGISTRY_SECRET_ARN`, and `AWS_SSM_DOCUMENT_NAME`.

The host timer can perform public metadata polling and healthy-receipt no-op checks without registry credentials. If it encounters a new private digest after the job credential has been cleared, pull fails closed and the active release stays in service. Retry a failed rollout by rerunning the failed `private-deploy` workflow, which receives a fresh job token and targets the same latest release under the source ancestry and receipt guards. There is no anonymous GHCR fallback or host PAT.
