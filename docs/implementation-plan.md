# 후로기 주루마블용 수집기 구현 계획 v3

수정: 2026-09-21. 사용자 확정 목적에 맞춰 v2의 우선순위와 범위를 교체했다.
**쿠키 획득·단일 채널 수집·후원 저장/재생·채팅·mTLS 전달과 정식 배포를 완료했다. 이 문서는 구현 단계와 제품 인수 기준을 보존하며, 단계별 검증 근거는 [구현 상태](implementation-status.md)를 따른다.**

| 단계 | 현재 상태 | 남은 확인 |
| --- | --- | --- |
| 1. 쿠키로 방송 연결 | 실제 로그인·다른 연령제한 방송 입장·채팅 확인 | h66rogi 본인 방송 수신 |
| 2. 수집 상태·재연결 | 상태 분리·방송 종료 대기·worker 강제 종료 후 재수신 확인 | 실제 시작→종료→다음 방송·네트워크 단절 전체 시나리오 |
| 3. 후원·채팅 전달 | journal/spool·11 RPC·별도 EC2 파일 inbox ACK/재생 확인 | 주루마블 실제 DB inbox·규칙·채팅 선택·화면 통합 |
| 4. 방송 운영·복구 | 정식 release·재부팅 복원·서버 인증서 회전·백업 업로드 확인 | 백업 복원·EC2 교체·운영 알림·소비자 인증서 갱신 연계 |

다음 제품 작업은 주루마블 소비자의 transaction inbox+cursor 저장→ACK 연결과 게임 인수 검사다.
수집기 쪽은 후로기 실방송을 기다리는 동안 복원/운영 검증을 진행할 수 있다.

## 1. rogimarble의 목적에서 정하는 수집기 역할

rogimarble는 후로기의 연령제한 방송에서 시청자의 별풍선 후원과 채팅 참여를
공유 말 하나의 보드 이동·미션·실드/보상으로 연결하고, 운영자가 웹 콘솔로 진행하며
시청자가 OBS 화면으로 결과를 보는 **방송용 주루마블 서비스**다.
초기 보드는 9×6 외곽 26칸이고, 후원 규칙·보드 동작·미션·연출은 서비스 설정으로 관리한다.

이 작업의 수집기는 그 서비스를 위한 방송 입력 도구다. `chat-collector`는 가져와 수정할 코드베이스이며,
원본이 지원하는 기능 목록이나 범용 수집기 완성도를 제품 요구사항으로 삼지 않는다.
기존 구조를 출발점으로 보존하는 것과 원본 제품의 범위를 목표로 삼는 것은 별개다.

### 방송 중 실제 사용 흐름과 필요한 입력

| rogimarble에서 일어나는 일 | 이 도구가 해야 하는 일 | rogimarble가 결정하는 일 |
| --- | --- | --- |
| 후로기가 연령제한 방송을 시작한다 | `h66rogi`만 감지하고 주입 쿠키로 입장, 연결 상태 전달 | 운영 화면의 방송/게임 준비 표시 |
| 시청자가 별풍선을 보낸다 | 후원자 ID·정확한 개수·종류·메시지·식별 정보를 보존해 전달 | 당시 설정의 정확한 개수 일치로 이동·미션·아이템 요청 생성 |
| 초기 설정의 33개 후원이 들어온다 | 33이라는 후원 사실을 한 건 전달 | 서버가 주사위와 공유 말 이동을 확정하고 OBS에 표시 |
| 원하는 칸 요청의 후원자가 채팅으로 칸을 고른다 | 후원 donorId와 동일 규칙의 userId, 메시지·시각을 전달 | 요청/본인/칸을 검증하고 운영자 선택과 합쳐 한 번만 확정 |
| 규칙에 없는 개수의 후원이 들어온다 | 게임 대상 개수로 필터링하지 않고 지원하는 후원을 모두 전달 | 후원 내역에 남기고 무동작 사유 표시 |
| 운영자가 자동 진행을 일시정지한다 | 수집과 전달 계속; 게임 pause를 수집 중지로 해석하지 않음 | 이동 대기·미션 확인·보상 조정·재개를 제어 |
| 게임 세션이 없거나 종료되어 있다 | 방송 입력의 채널/시각을 보존하고 임의 세션을 붙이지 않음 | 채널 후원 내역에 기록하고 새 세션으로 자동 소급하지 않음 |
| 쿠키/네트워크 문제로 수집이 끊긴다 | 끊김과 원인·마지막 수신을 전달, 복구 후 저장한 후원 재전송 | 수집 상태 안내, 수동 진행 유지, 같은 후원 중복 게임 실행 방지 |

33·486 등은 초기 설정 예시다. 개수별 게임 기능이나 `!이동` 파싱은 collector에 넣지 않는다.
채팅이 후원보다 먼저 전달될 수도 있으므로 주루마블이 명령 후보를 잠시 보관해 요청과 대조한다.
수집 쿠키의 로그인 계정은 수신한 채팅/후원의 작성자 신원과 별개다.
수동 주사위·실드 조정은 operator 명령이며 가짜 후원으로 만들지 않는다.
OBS 연결/애니메이션 완료는 후원 수락이나 게임 결과 확정의 조건이 아니다.

### 이 작업에서 만들 동작

**후로기(`h66rogi`)가 SOOP에서 연령제한 방송을 켜면 자동으로 감지하고,
주입한 로그인 쿠키로 접속해 그 방송방의 채팅과 주루마블에 필요한 별풍선 후원을 전달한다.**

- 대상은 `h66rogi` 한 채널이다. 채팅은 그 방의 시청자 메시지 전체이며, 작성자가 후로기인 메시지만 거르는 것이 아니다.
- 방송이 꺼져 있으면 기다리고, 켜지면 연결하고, 끊기면 다시 연결한다.
- 연령제한 방송 접속이 첫 구현의 핵심이다. 일반 방송에 익명 접속하는 데 성공한 것으로 대체하지 않는다.
- 쿠키 만료로 수집할 수 없으면 운영자가 원인을 알아보고 쿠키 교체 후 다시 연결할 수 있어야 한다.
- 주루마블이 후원자의 별풍선 개수와 채팅을 받아 기존 게임 규칙을 실행할 수 있어야 한다.
  후원도 기존 목표에 포함하며 채팅만 수집하는 제품으로 축소하지 않는다.

원본 8개 모듈과 discover → coordinator → worker → query 구조는 유지한다.
수집 대상과 인증 방식을 이 제품에 맞게 수정한다. 새 수집기를 별도로 재작성하지 않는다.
초기에는 코드 구현과 CI/CD를 분리했으며, 후속 사용자 요청으로 이 작업에서 정식 배포까지 연결했다.
현재 배포 경로는 [운영 문서](deployment-production.md), 게임 구현의 경계는 아래 3단계를 따른다.

## 2. 첫 버전의 범위

| 이번에 필요한 것 | 지금 먼저 만들지 않을 것 |
| --- | --- |
| 후로기 한 채널의 자동 방송 감지 | 임의 채널 등록·승인 서비스, 다채널 탐색 |
| ID/PW 로그인·일일/요청 시 쿠키 갱신·수집기 주입 | 여러 계정 관리 서비스 |
| 그 방의 채팅·별풍선 수신 | 다른 플랫폼 지원 확대·전체 채팅 검색/분석 |
| 주루마블 한 소비자에게 전달 | 여러 제품 구독 관리 화면·범용 권한 관리 기능 |
| 연결 상태와 쿠키 문제 안내 | 연결 확인 전 대규모 관측/운영 체계 구축 |
| 후원 저장·재전송·중복 게임 실행 방지 | 다중 worker 확장·무중단 소유권 이동 고도화 |

한 채널이라는 조건은 제품 설정에 둔다. parser나 게임 로직 곳곳에 계정명을 하드코딩하지 않는다.
현재 `CHANNEL_ALLOWLIST`를 재사용해 이 제품에서는 `soop:h66rogi`만 설정하고,
discover뿐 아니라 할당/worker 접속에서도 대상 밖의 채널을 막는다. 미설정은 수집 중지다.
예전 DB에 다른 채널의 할당이 남아 있어도 접속하지 않는다. 테스트에는 가상의 채널/쿠키를 사용한다.

기존 [배포·소비 계약](deployment-design.md)의 공통 구조와 후원 전달 의미는 유지한다.
다만 일반화된 기능을 모두 끝낸 후 실제 방송 연결을 시도하던 v2 순서는 이 계획으로 대체한다.

## 3. 원본에서 확인한 변경 필요 지점

| 반입 전 원본 코드 | 당시 제품 요구와의 차이 | 적용한 수정 방향 |
| --- | --- | --- |
| `discover/internal/discovery/soop.go`의 `IsChannelLive` | 쿠키 없는 요청, CHATNO가 없으면 곧바로 offline | 인증된 상태 조회, 방송 종료/인증 필요/조회 실패 구분 |
| `worker/internal/connector/soop.go`의 `fetchChannelInfo` | 쿠키 없이 채팅 접속 정보를 요청 | 같은 쿠키 공급 방식으로 접속 정보 조회 |
| 같은 connector의 login/join | login 응답 후 join 전송만으로 연결 성공 처리 | 실제 입장 응답 의미를 확인해 입장 실패/성공 구분 |
| `worker/internal/connector/factory.go`, 두 역할의 `cmd/main.go` | 쿠키 설정 전달 경로 없음 | 기존 생성자/설정에 쿠키 provider 연결 |
| `worker/internal/manager.go` | 기존 연결·재접속 틀은 있음 | 쿠키 교체 후 재시도와 원인별 상태를 연결 |
| connector의 `emitMessage`, 기존 publisher | 버퍼가 차면 후원도 drop, raw hash 중복 제거 | 후원은 이 경로 이전에 분리해 저장 |
| 원본 후원 변환 | 종류를 합쳐 별풍선 취급, 연결별 ID 재사용 | native 개수/종류/안정적인 ID를 보존 |

쿠키를 Cookie 헤더에 넣는 것만으로 모든 접속 단계가 해결된다고 가정하지 않는다.
인증된 player 응답, FTK/접속 정보, WebSocket login/join 중 실제로 필요한 단계부터 확인하고 수정한다.
SOOP 응답 코드·인증 필드의 의미는 아직 확인하지 않은 부분을 추정해 구현하지 않는다.

## 4. 구현 순서

아래는 각 단계의 구현 요구와 인수 절차다. 문장의 요구형 표현 자체가 미구현을 뜻하지 않으며 현재 완료 범위는 위 표와 검증 기록을 따른다.

### 1단계 · 후로기 방송에 쿠키로 연결해 채팅 받기

사용자 추가 요구로 [쿠키 획득 컴포넌트](../cookie-auth/README.md)를 구현했다.
`SOOP_ID`/`SOOP_PW`는 이 컴포넌트만 받고, 시작 시/마지막 성공 후 24시간/명시적 갱신 요청 시 로그인한다.
성공한 쿠키는 domain/path/expiry를 가진 JSON snapshot으로 저장하고 기존 discover/worker가 읽는다.
갱신 실패는 기존 쿠키를 덮어쓰지 않는다. 원본 조사 근거는 [비교 기록](cookie-acquisition-review.md)에 있다.
쿠키 확보와 방송 입장은 별도 검사다. 다른 연령제한 방송에서는 둘 다 확인했고, 후로기 방송 수신은 남아 있다.

**첫 결과물:** 대상 방송이 켜지면 기존 worker가 입장하고 채팅 이벤트를 받는다.

수정 위치는 기존 SOOP discovery/connector/factory, discover·worker entrypoint다.
공통 쿠키 읽기/요청 적용 코드는 `shared` 안에 작게 추가해 두 역할에서 재사용한다.

- 첫 실행 설정은 한 채널과 쿠키 파일 경로다. `SOOP_COOKIE_FILE`에 컴포넌트가 쓰고 수집기가 읽는 JSON 파일 경로를 둔다.
  수집용으로 제공받은, 연령제한 방송에 접근 가능한 로그인 세션을 사용한다.
  방송 대상 계정과 쿠키의 로그인 계정이 반드시 같다고 가정하지 않는다.
- 파일 형식은 쿠키 획득 시각과 domain/path/expiry를 포함하는 version 1 JSON snapshot이다.
  누락·잘못된 형식·만료는 인증 요청 오류로 드러나며, 운영 화면의 상태 연결은 후속 작업이다. 실제 값은 저장소·문서·명령 인자에 넣지 않는다.
- discover의 방송 확인과 worker의 접속 정보 조회 모두 쿠키를 사용할 수 있게 한다.
  요청/재연결 시 파일을 다시 읽어 교체를 반영한다. 파일 변경은 완성된 파일의 원자적 교체를 전제로 한다.
- 쿠키는 확인된 SOOP 인증 요청에만 보낸다. 다른 호스트 redirect나 플랫폼 응답이 지정한
  임의 WebSocket 호스트에 그대로 전달하지 않는다. WebSocket 인증 전달은 실제 필요 필드/범위 확인 후 적용한다.
- 방송 종료와 인증 실패를 분리한다. CHATNO 부재만으로 종료로 확정하지 않고,
  알 수 없는 응답은 `연결 확인 실패`로 남긴다. 거절된 입장을 수집 중으로 표시하지 않는다.
- 원본 frame/parser/keepalive/reconnect를 사용해 채팅을 수신한다.
  인증 실패는 빠른 재시도 반복 대신 제한된 재시도로 대기하고 쿠키 교체 후 다시 확인한다.

**검증:** 합성 HTTP/WebSocket으로 대상 제한, 쿠키 전달, 인증 거절, join 실패/성공을 먼저 확인한다.
이어 제공된 쿠키가 준비되면 **실제 후로기의 연령제한 방송에서 채팅 수신을 조기에 확인**한다.
쿠키가 없거나 방송이 꺼져 있으면 실제 접속 항목만 미검증으로 남기고 합성 검증·후속 코드 작업은 진행한다.
원문 쿠키/FTK를 로그나 fixture에 남기지 않는다. 실제 접속 검증 전에 기능을 지원 완료라고 표시하지 않는다.

### 2단계 · 방송 시작·종료·쿠키 만료를 운영 가능한 동작으로 만들기

**결과물:** 방송할 때 자동 연결되고, 문제가 나면 무엇을 해야 하는지 알 수 있다.

기존 discover loop, coordinator 할당, worker manager와 query 상태 응답을 연결한다.

| 운영자에게 전달할 상태 | 동작 |
| --- | --- |
| 방송 대기 | 일정 간격으로 후로기 방송만 확인 |
| 연결 중 | 접속 정보 조회와 입장 진행 |
| 수집 중 | 입장 확인, 최근 채팅/후원 수신 시각 제공 |
| 쿠키 설정 필요 / 인증 확인 필요 | 수집 불가 원인 표시, 쿠키 교체 후 재확인 |
| 재연결 중 | 일시적인 네트워크 단절 후 기존 backoff로 재연결 |
| 저장 지연 / 수집 중단 | 후원 저장 문제와 미수집 가능 구간 표시 |

- 인증 실패만으로 정확한 만료/연령 인증 원인을 단정하지 않는다. 확인된 응답 근거만 안내한다.
- 정상 방송 종료 뒤 다음 방송을 다시 찾는다. 인증/조회 실패로 잘못 종료 처리하지 않는다.
- 연결되지 않았는데 프로세스가 살아 있다는 이유로 `수집 중`이라고 하지 않는다.
  채팅이 조용한 상태와 입장 실패도 구분한다.
- worker 재시작으로 같은 채널에 중복 연결하지 않게 기존 owner/lease 틀을 사용한다.
  첫 실행은 worker 1개이며 다중 worker 기능 확대를 이 단계의 선행 조건으로 두지 않는다.

**검증:** 방송 시작→채팅 수신→연결 단절→재연결→방송 종료→다음 방송,
인증 실패→쿠키 파일 교체→접속 재확인을 실제 역할과 합성 서버로 반복한다.

### 3단계 · 후원으로 게임을 진행하고 후원자 채팅으로 목적지 선택하기

**제품 연결 결과물:** 후원이 내역에 표시되고 설정에 맞는 게임 요청으로 이어지며, 원하는 칸 요청의 후원자가 채팅으로 선택할 수 있다.
이 작업은 이를 위한 수집/전달을 맡고 게임·웹·OBS 동작은 rogimarble 구현과 함께 통합 확인한다.

- 기존 query 서버에 collector v1을 연결한다. 기존 계약/생성 도구를 보완하고
  주루마블이 사용하는 상태·채팅 구독·후원 목록/구독·ACK 경로부터 동작시킨다.
- 채팅 userId와 후원 donorId의 정규화 규칙을 맞춘다. 닉네임으로 사용자를 추정하지 않는다.
- 별풍선 native 정수 개수·종류·메시지를 보존한다. 원화 환산이나 collector 내부의 게임 규칙 매칭은 하지 않는다.
  확인되지 않은 다른 후원 종류를 별풍선으로 뭉뚱그리지 않는다.
- 후원을 connector의 drop 경로에서 먼저 분리한다. 기존 PgStore에 후원 journal/outbox를 추가하고,
  한 채널의 수락 순서를 직렬화해 저장한 순서대로 제공한다. 안정적인 eventId를 재전송에도 유지한다.
- 채팅은 기존 Redis stream을 재사용한다. 주루마블이 잠시 중단되어도 후원은 DB에 남겨 다시 전달한다.
- 주루마블은 자신의 inbox에 저장한 뒤 ACK하고 같은 eventId의 게임 효과를 중복 실행하지 않는다.
  서로 다른 정상 동일 개수 후원 두 건은 둘 다 전달한다. 원천 ID 없는 재접속 의심은 품질 정보로 전달한다.
- 외부 전달은 기존 설계대로 인증된 내부 gRPC로 한다. 첫 소비자는 주루마블 하나로 설정하고,
  신원/채널 검증을 적용한다. 범용 consumer 등록/권한 관리 시스템을 먼저 만들지 않는다.
- 기존 11개 RPC 계약은 보존한다. 구독 변경은 허용된 한 채널의 시작/중지로 제한하고
  동적 채널 발굴·승인 기능을 넣지 않는다. 실제 사용하지 않는 원본 광역 조회/관리 endpoint는 노출하지 않는다.

**검증:** 합성 채팅/별풍선이 실제 query→주루마블 inbox까지 들어오는 경로를 확인한다.
소비자 재시작·ACK 응답 유실에도 누락/중복 게임 실행이 없는지 확인한다.
제품 인수 기준은 다음과 같다. 각 기준은 합성 입력으로 반복 확인하고 실제 방송 관측 여부를 별도로 기록한다.

- 초기 33개 후원 한 건이 주사위 요청 한 건으로 연결되고 재전송이 새 요청을 만들지 않는다.
  정상 33개 후원 두 건은 두 요청이며, 미등록 66개를 두 번으로 환산하지 않는다.
- 규칙에 없는 후원도 내역에 표시된다. 규칙을 바꿔도 collector 수정 없이 입력을 계속 전달한다.
- 초기 486개 후원의 본인 채팅이 원하는 칸 선택으로 이어진다. 다른 시청자의 입력은 확정하지 못하고,
  운영자 선택과 경합해도 한 번만 확정된다. 후원/채팅 역순도 확인한다.
- 게임 일시정지 중에도 후원이 보존된다. 세션 밖의 후원을 다음 게임에 임의 배정하지 않는다.
- 수집이 끊겨도 운영자는 웹의 수동 주사위·보상 조작을 사용할 수 있고, 재연결/OBS 새로고침으로 결과가 중복되지 않는다.

게임/운영 화면 구현은 rogimarble 작업이 맡는다. collector 단독 시험 통과로 위 통합 동작까지 완료했다고 하지 않는다.

### 4단계 · 한 번의 방송을 운영할 수 있도록 마무리하기

**결과물:** 방송 중 연결/저장 문제가 드러나고, 복구 후 이미 처리한 후원을 다시 실행하지 않는다.

- DB 장애 때 후원을 제한된 disk spool에 저장하고 복구 시 같은 eventId로 journal에 이관한다.
  full/손상 때 조용히 버리지 않고 저장 실패/수집 중단으로 알린다.
- 후원 수락 지점에서 현재 owner를 검사한다. 재시작 전 worker의 늦은 쓰기와 과거 spool 이관을 구분하고,
  수락 권한을 확인할 수 없는 항목은 자동 적용하지 않는다.
- ACK는 앞선 후원까지 저장한 연속 위치까지만 전진한다. 보존 범위 밖/DB 복원 뒤에는
  자동 최신 점프나 재적용 없이 멈추고 기존 recovery 계약으로 명시적 재개점을 정한다.
- journal·chat·spool은 유한 보존으로 설정한다. 주루마블 화면에는 수집/저장 문제와 복구 필요 상태를 전달한다.
- 쿠키 교체, 프로세스 재시작, 주루마블 일시 중단을 포함해 실제 방송 운영 흐름으로 점검한다.
  실제 금전 후원을 자동 생성하지 않고 합성 후원 검증과 실제 관측 증거를 구분한다.

이는 출시 전 필요한 마무리다. 1단계의 실제 연결 확인을 이 항목들이 모두 끝날 때까지 미루지 않는다.
세부 장애 시험은 해당 변경 시 작성하고 별도 범용 플랫폼 구축 작업으로 확대하지 않는다.

## 5. 문서·배포 작업과의 경계

- 원본 반입 기록·LICENSE/NOTICE·8개 모듈·기존 테스트는 유지한다.
- SQL/계약 변경은 해당 기능 단계에서 필요한 만큼 한다. 이미 적용된 migration을 덮어쓰지 않는다.
- 기존 `make build/test/race/source-check`를 활용하고 실제 저장소/플랫폼 시험은 별도로 실행한다.
- CI/CD 담당에는 `<role>/cmd`, 한 채널 설정, **discover와 worker에 필요한 쿠키 파일 mount**,
  내부 gRPC/저장소 설정과 probe 차이를 [인계 문서](collector-code-handoff.md)에 전달한다.
- 로그인 ID/PW 공급과 컴포넌트 배포는 운영 입력이다. 코드에서는 쿠키를 획득/갱신하고 파일을 읽는 기능을 제공한다.
  수집 쿠키를 주루마블 브라우저나 query 응답에 전달하지 않는다.

상위 계획과 연결할 때 1~2단계는 C01, 3단계는 필요한 P03/C02/C03/I02,
4단계는 C02/C03의 출시 검증에 해당한다. 작업 ID 순서보다 위 제품 동작을 먼저 연결한다.

**다음 인수 검사는 주루마블 실제 inbox/게임 연결과 `h66rogi` 실방송 수신이다.**
백업 복원·호스트 교체와 운영 알림은 별도 운영 검증으로 남긴다. 단계별 상세 결과는 [구현 상태](implementation-status.md)를 갱신한다.
